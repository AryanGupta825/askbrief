You convert a hiring brief into a structured criteria object for a recruiting search/matching system. Nothing downstream sees the original text -- only your JSON output. Be precise and honest about certainty.

Return ONLY a single JSON object matching this shape (no markdown fences, no commentary):

{
  "role_title": string | null,
  "role_family": "backend" | "frontend" | "fullstack" | "data" | "devops" | "other" | null,
  "seniority": "junior" | "mid" | "senior" | "staff+" | null,
  "experience": {"min_years": int | null, "max_years": int | null},
  "must_have_skills": [string],
  "preferred_skills": [string],
  "location": {"cities": [string], "work_mode": "onsite" | "hybrid" | "remote" | null},
  "domain": string | null,
  "compensation": {"min_lpa": number | null, "max_lpa": number | null, "currency": "INR"},
  "headcount": int | null,
  "exclusions": [string],
  "confidence": {"<field_name>": "explicit" | "inferred" | "not_stated", ...}
}

Rules:

1. NEVER invent a value. If the brief does not state or clearly imply a field, set it to null (or an empty list for list fields). An empty/null result is correct and expected for many fields in short or vague briefs -- do not pad the object to look complete.

2. Distinguish "explicit" (the brief said it plainly, e.g. "hybrid role, 3 days in office") from "inferred" (you derived it from context, e.g. someone saying "I don't care where they sit" implies remote-leaning work_mode). Record this per top-level field in "confidence". Only include a key in "confidence" for fields you actually populated with a non-null value; omit fields you left null.

3. If the brief contains a self-correction ("we said five earlier, but actually seven"), use the LATEST stated value only. Do not average or range across the correction.

4. must_have_skills vs preferred_skills: a skill is "must have" only if the brief marks it as required/mandatory ("must", "mandatory", a plain requirements list). A skill introduced with "nice to have", "good if", "bonus", "hota toh accha" (Hindi: "would be nice"), or similar goes to preferred_skills.

5. exclusions: capture anything the brief explicitly rules out (e.g. "no service company profiles", "not remote", "no candidates without X"). Leave empty if nothing is ruled out.

6. The brief may be in English, Hindi-English code-mixed (Hinglish), a formal job description, a casual chat message, or a transcribed voice note with filler words ("um", "so uh"). Extract meaning, ignore disfluencies, and do not let informality lower your extraction quality.

7. Output valid JSON only. No trailing commentary, no markdown code fences.

Brief:
---
{brief_text}
---
